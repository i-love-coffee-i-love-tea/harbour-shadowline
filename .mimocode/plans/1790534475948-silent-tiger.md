# Fix timezone detection for location current time

## Problem

Berlin shows the wrong current time. Multiple attempts to use `Intl.DateTimeFormat` with `timeZone` option have failed on the QML V4 engine (Qt 5.6.3 on Sailfish OS). The engine either:
- Doesn't support `Intl.DateTimeFormat` at all (catch block silently falls back to longitude-based UTC+1 for Berlin)
- Supports `Intl.DateTimeFormat` but ignores the `timeZone` option
- Supports `Intl.DateTimeFormat` but `hour12: false` isn't respected (12h format without AM/PM)

The longitude-based fallback uses `Math.round(lon/15)` which gives UTC+1 for Berlin (13.4°E) — but Berlin is UTC+2 in summer (CEST). No DST handling.

## Root cause

The QML V4 engine in Qt 5.6 has incomplete or non-functional ECMA-402 (Intl) support. The `timeZone` option in `Intl.DateTimeFormat` is not reliably supported. All approaches relying on it will fail silently.

## Solution

**Abandon `Intl.DateTimeFormat` entirely. Store UTC offset + DST flag directly in the city data, compute local time from UTC mathematically.**

### Files to modify

1. **`qml/pages/LocationPicker.qml`** — Replace `cityTz` map (IANA timezone IDs) with `cityOff` map (UTC offset + DST flag)
2. **`qml/components/LocationListItem.qml`** — Replace `_getTzOffset`/`_getLocalTime` with pure-UTC arithmetic. Fix sunrise/sunset display to use location timezone instead of system timezone.
3. **`qml/pages/MainPage.qml`** — Update property name from `locationTz` to `locationOff` in the delegate binding
4. **`qml/components/LocationListItem.qml`** — Update property name from `locationTz` to `locationOff`

### Step 1: Replace cityTz with cityOff in LocationPicker.qml

Replace the `cityTz` map with a `cityOff` map where each entry stores `{o: <standard_utc_offset_hours>, d: <dst_flag>}`:

```qml
readonly property var cityOff: ({
    "Abu Dhabi":   {o:  4, d: 0},   // no DST
    "Abuja":       {o:  1, d: 0},
    "Accra":       {o:  0, d: 0},
    // ...
    "Berlin":      {o:  1, d: 1},   // CET/CEST
    // ...
    "Cairo":       {o:  2, d: 0},   // no DST
    // ...
})
```

`o` = standard UTC offset in hours (winter for DST-observing regions)
`d` = 1 if the city observes DST, 0 if not

The signal emission changes from `tz: cityTz[name]` to `off: cityOff[name] || {o: 0, d: 0}`.

### Step 2: DST detection using solar declination (in LocationListItem.qml)

Use the solar declination from `Solar.solarData()` as a proxy for "is it summer":
- Solar declination > 0 → summer in northern hemisphere
- Solar declination < 0 → summer in southern hemisphere

DST adds +1 hour when:
- `dst_flag == 1` AND
- City latitude > 0 AND solar declination > 0 (northern summer), OR
- City latitude < 0 AND solar declination < 0 (southern summer)

This is an approximation — DST transitions don't align exactly with the equinoxes (they're ~2 weeks off in some countries), and not all countries use +1h DST. But it's far better than the current approach which shows completely wrong times.

### Step 3: Compute local time from UTC

```javascript
function _getLocalTime(off, lat, lon) {
    var now = new Date();
    if (off) {
        var utcH = now.getUTCHours();
        var utcM = now.getUTCMinutes();
        var utcS = now.getUTCSeconds();
        var utcMs = utcH * 3600000 + utcM * 60000 + utcS * 1000;
        
        // Check DST: is it summer at this latitude?
        var data = Solar.solarData(now, lat, lon);
        var dstActive = off.d === 1 && (
            (lat > 0 && data.declination > 0) ||
            (lat < 0 && data.declination < 0)
        );
        
        var offsetHours = off.o + (dstActive ? 1 : 0);
        var localMs = utcMs + offsetHours * 3600000;
        
        // Wrap to 24h
        if (localMs < 0) localMs += 86400000;
        if (localMs >= 86400000) localMs -= 86400000;
        
        var h = Math.floor(localMs / 3600000);
        var m = Math.floor((localMs % 3600000) / 60000);
        return (h < 10 ? "0" : "") + h + ":" + (m < 10 ? "0" : "") + m;
    }
    // Fallback: longitude-based
    ...
}
```

### Step 4: Fix sunrise/sunset display

`Solar.formatTime(data.sunrise)` uses `date.getHours()` which returns system-local time, not the location's local time. This has always been wrong when the system and location timezones differ.

Fix: compute the location's local time from the UTC value of the sunrise/sunset Date objects:

```javascript
function _formatLocationTime(utcDate, off, lat) {
    if (!utcDate) return "--:--";
    var utcMs = utcDate.getUTCHours() * 3600000 + utcDate.getUTCMinutes() * 60000;
    var data = Solar.solarData(new Date(), lat, 0); // for declination
    var dstActive = off.d === 1 && (
        (lat > 0 && data.declination > 0) ||
        (lat < 0 && data.declination < 0)
    );
    var offsetHours = off.o + (dstActive ? 1 : 0);
    var localMs = utcMs + offsetHours * 3600000;
    if (localMs < 0) localMs += 86400000;
    if (localMs >= 86400000) localMs -= 86400000;
    var h = Math.floor(localMs / 3600000);
    var m = Math.floor((localMs % 3600000) / 60000);
    return (h < 10 ? "0" : "") + h + ":" + (m < 10 ? "0" : "") + m;
}
```

### Step 5: Database migration

The `locations` table has a `tz` column (text, IANA ID). Change semantics:
- New column: `off_o INTEGER DEFAULT 0` (UTC offset hours), `off_d INTEGER DEFAULT 0` (DST flag)
- Migrate existing `tz` data by looking up the offset from a mapping, or just reset it

Simpler: reuse the existing `tz` column as a JSON string like `"1,1"` (offset,dst) or add two new integer columns.

### Step 6: Remove unused Intl code

Delete `_getTzOffset()` function entirely. Remove all `Intl.DateTimeFormat` references from `LocationListItem.qml`.
